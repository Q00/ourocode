Interpretation and gate
-----------------------

`PageBudget.reserved_bytes` is deliberately a virtual-mapping admission
counter. The exact pin keeps every compressed page's raw virtual mapping and
uses `madvise(FREE_REUSABLE)` to discard its physical contents. This preserves
the current infallible, allocation-free restore contract, so compression must
not reduce `reserved_bytes`. Raw RSS and resident virtual bytes include clean,
reclaimable mappings and are not the RFC physical-footprint gate.

The product's 32 x 10,000 app-core target of at most 150 MiB is satisfied by
the measured 50.1 MiB steady physical footprint. A different requirement that
`PageBudget.reserved_bytes` itself be at most 150 MiB is incompatible with the
retained-mapping contract: using a 157,286,400-byte PageBudget failed closed at
session 14, feed chunk 17, with 152,338,432 bytes reserved, 495 denials, and no
child failure. Incremental compression cannot change that admission result.

Meeting a 150 MiB raw-mapping requirement without deleting scrollback needs an
upstream architecture change: release compressed raw mappings, make every
restore path fallible, and propagate allocation failure through callers; or
add a bounded shared restore cache with explicit eviction and pointer-lifetime
rules. Redefining the existing reserved counter as physical dirty memory would
hide the retained VAS and weaken its hard admission contract, so this change
was not made.
